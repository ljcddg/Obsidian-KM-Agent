# Feature · Architecture Locking（知识架构锁定）

> 目标：**防止分类反复变化导致知识库混乱**。大规模 vault 最怕的不是没有分类，而是"第 1 个月叫 Java/并发，第 6 个月改成 Backend/Java/Concurrency，第 12 个月又改 Programming/Language/JVM"——每次改名都是一场迁移灾难。本机制锁定架构状态，让变更可控。

## 架构状态（Architecture Status）

每 100 篇笔记或每季度，评估一次架构状态：

| 状态 | 含义 | 允许的操作级别 |
|------|------|:---:|
| `experimental` | 新 vault / 新建分类，允许试错 | L0+L1 自动，L2+L3 需确认 |
| `stable` | 分类体系成熟，进入维护期 | L0+L1 自动，L2 需确认，L3 禁止自动 |
| `frozen` | 冻结，只允许增补内容 | **仅 L0+L1**（创建笔记 + 补元数据） |
| `migration` | 正在执行大规模调整 | 仅执行已批准的迁移清单 |

**状态切换规则：**
- 新 vault 或全新领域 → `experimental`
- `experimental` 下连续 30 天无分类变更 → 自动或手动切 `stable`
- `stable` 下稳定运行 >1 年、笔记数 >100 → 用户可选择切 `frozen`
- `stable` 下变更 ≥5 个文件的目录 → 先切 `migration` 再执行
- `migration` 完成后 → 切回 `stable`

**权限细则见 `features/modification-rules.md`。**

## 稳定性原则

> **新知识适应旧结构，而不是旧结构不断适应新知识。**

- stable/frozen 状态下，新建笔记归入已有分类——如果放不下，**扩展已有子目录，而不是新建一级分类**。
- 看到分类可以优化 → 把思路记下来，不要当场动手；满 6 个月再评估是否值得 migration。
- frozen 下 Agent 的角色从"管理者"切换为"助手"：创建、补元数据、检索——不碰结构。

## 迁移方案规范（stable → migration → stable）

1. **评估必要性**：问三个问题——
   - 当前的分类带来了什么实际问题？（找不到文件 / 重复严重 / 无法扩展）
   - 新方案能解决吗？
   - 迁移成本（受影响文件数 × 每文件操作步骤）值得吗？

2. **生成迁移清单**（必须征得确认）：

```markdown
## 迁移方案：{{名称}}

### 现状
- 3-概率结构/ → 无对应顶层领域
- 2-树形结构/ → 可并入"数据结构"大类

### 目标
- 新建：数据结构/  → 合并 树形结构 + 概率结构 为子目录
- 保留：1-线性结构/、4-Java容器源码/、5-并发多线程/

### 受影响文件（共 N 篇）
| 原路径 | 新路径 | 需要更新的引用 |
|------|------|-------------|
| 2-树形结构/红黑树.md | 数据结构/树形结构/红黑树.md | MOC、Stack知识点的 [[ ]] |
| ...    | ...  | ...    |

### 执行步骤
1. 备份（cp -r 整体备份）
2. mkdir 新目录
3. mv 迁移文件
4. 更新受影响笔记的 [[ ]] 引用
5. 更新 MOC 与 .vault-meta
6. 删除空旧目录
```

3. **执行**：按清单逐条，每批 ≤10 个文件，完成一批验证一批。

## 防回退机制

- 迁移完成后标记 `architecture_status: stable`。
- 同一条目 90 天内不再次迁移（避免 ping-pong 改名）。
- 如果用户拒绝迁移方案，把方案存档（不执行），6 个月后再评估。

## 与三层管理的关系

目录层受架构锁定保护（最重）。**元数据层（frontmatter tags）和关系层（[[ ]]）不受锁定**——这两个维度可以随时调整，不影响物理文件，不会造成迁移灾难。如果一个内容在两个分类之间摇摆，优先用 tags 和 [[ ]] 建立多维度关联，而不是改目录。
