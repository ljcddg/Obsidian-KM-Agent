# Workflow · Write（结构化写作）

## 核心：要素按等级裁剪

要素：**痛点 / 为什么 / 机制 / 原理 / 对比 / 坑 / 自测**。**不是每篇都要全**——按等级取用，防止过度膨胀；但「原理」对 L2/L3 是必写，不许裁掉：

| 要素 | L1 速记 | L2 知识点 | L3 专题 |
|------|:------:|:------:|:------:|
| 痛点开头 | 可选（一句话） | ✅ | ✅ |
| 为什么需要 | — | ✅（重点） | ✅ |
| 核心机制/定义 | ✅ | ✅ | ✅ |
| **实现原理/底层机制** | — | ✅（必写） | ✅（必写） |
| 对比表 | — | ✅ | ✅ |
| 陷阱与坑 | — | ✅ | ✅ |
| 自测题 | — | 3~8 道 | 5~15 道 |
| SVG 结构图 | — | 可选 | ✅ |
| MOC/学习路线 | — | — | ✅ |

## 各要素写法

### 1. 痛点开头（L2/L3）
- 格式：`{{主题}}是……，但 {{常见困惑或坑}}，导致 {{后果}}。本文从 {{角度}} 讲清 {{目标}}。`
- 第一段就要让读者觉得"这就是我卡住的地方"，不要从定义开始。
- L1 可只用一句话点题，不强行制造痛点。

### 2. 为什么需要（L2/L3 的灵魂，占最大篇幅）
- 先讲"它解决了什么问题 / 不解决会怎样"，**再**给定义。
- 用具体场景引出：不要"XXX 是一个同步辅助类"，要"5 个任务并行，主线程不知道何时继续 → 需要一个计数器 → 这就是 XXX"。
- 自然引出机制，理解随之形成。

### 3. 定义与核心机制
- 定义压缩成 1~2 行，术语保留原文（如 `Deque`、`ReentrantLock`）。
- 机制讲"怎么做"：输入 → 步骤 → 输出，配精简示例。

### 3.5 实现原理 / 底层机制（L2/L3 必写，不许省略）
- **目的**：面试考的是"为什么这么实现"，不是"怎么用"。`synchronized` 要答到对象头 Mark Word + monitorenter + ObjectMonitor；`CAS` 要答到 `Unsafe.compareAndSwapInt` + 自旋 + ABA。
- **写法**：讲清"底层为什么"——① 数据结构（对象头 / AQS 队列 / 位数组…）② 关键指令或方法（monitorenter / cmpxchg / compareAndSet…）③ 核心实现类与源码位置（`ObjectMonitor` / `Unsafe` / `AQS#acquire`…）④ 一句话讲透机制本质。
- **边界**：原理写到"能应对面试追问 + 不编造细节"即可；无把握的实现细节标注 `❓待验证`（见 `features/fact-check.md`），**严禁凭空编造**。
- 代码类主题还须满足 `references/coding-note.md` 五要素中的「核心源码位置与实现原理」。

### 4. 对比表（凡是易混，必须上表）
```markdown
| 维度 | {{对象A}} | {{对象B}} |
|------|-----------|-----------|
| 本质 | | |
| 适用场景 | | |
| 优缺点 | | |
| 怎么选 | | |
```
- 至少 3 个维度（本质/场景/取舍），只列"是什么"的对比表没有价值。

### 5. 陷阱与坑
- 格式：`❌ 错误写法/理解 → 为什么错 → ✅ 正确写法/理解 → 原因`。
- 来源：常见误区、初学者的典型错误、边界条件（空/满/并发/溢出）。

### 6. 自测题（答案写作 / 折叠 / 样式完整规范见 `references/self-test-answers.md`）
- 题型：简答（讲原理）、辨析（A 与 B 的区别）、场景题（XX 场景用哪个）。
- 数量：L2 3~8 道、L3 5~15 道；必须覆盖本篇所有小节（含实现原理），写完按 `workflow/review.md` 自查。
- 题目：编号列表；题干把关键词/对象加粗（如 `1. **Function Calling 的三步流程是什么？**`），一眼能抓住考点。
- 答案：**两种形态，按所在系列统一，同一篇内不许混搭**——
  - **开放式（无答案）**：只有题目列表，答案留给读者闭卷自测（如 8-计算机网络 / 7-JVM 多数系列）。
  - **折叠式（带答案）**：答案收进 Obsidian 折叠 callout，点击才展开。**默认「一题一折叠」**（题目下紧跟它自己的答案）；若该系列历史笔记是"题目列表 + 整体折叠"，跟随系列。格式样例：
```markdown
1. **Function Calling 的三步流程是什么？大模型怎么"知道"有哪些函数可调？**

> [!answer]- 参考答案（点击展开）
> - ① 应用把 `@Tool` 方法生成 **JSON Schema** 放进请求 `tools` 数组发给模型
> - ② 模型判断"该不该调、传什么参"，返回 `tool_calls`（**只声明不执行**）
> - ③ 应用真正执行方法，把结果作为 tool 消息**回喂**模型，模型据此生成最终回答
> - 模型"知道" = 每次请求 `tools` 都带全量函数 schema
```
  - **带答案就必须给全**：同一篇所有题号都要有对应答案，不许只给几题。
  - **答案只从正文提炼**：数值、公式、代码引用与正文一致，禁止另编。
  - **答案版式一点一行**：折叠区里用 `> - ` 逐点成行（流程按步骤、辨析分对象、要点逐个列），关键点加粗；禁止用 `① ② ③` 挤成一整行。
  - **callout 类型用 `[!answer]`**（语义 = 答案，且能被专属 CSS 选中定制）；想让答案区有专属配色/字号（teal 青、小一号等），把 `assets/自测答案样式.css` 复制进 vault `.obsidian/snippets/` 并启用，见 `references/self-test-answers.md` §三。
- 动笔前先翻该分类下最近一篇成熟笔记的自测题，**跟随它的形态与样式**，保持系列一致。

### 7. 可视化（表格优先，图一律 SVG）

- **架构总览 / 分类对比类内容优先用表格**（如"接口 | 线程安全实现 | 线程不安全集合"三列式）。
- 需要图时**一律画成独立 SVG 文件**（`![[xxx.svg]]` 嵌入，与笔记同目录），**不使用 mermaid、不使用 ASCII 文本框图**——规范见 SKILL.md 第八章。
- 一张图只讲一件事：节点 > 12 就拆图；图后配 2~4 行文字解读，图才有意义。
- 出图后用无头 Chrome 截图自查溢出、压线、裁切（SKILL.md 8.5）。

## 写作风格红线

- **客观、命令式**：少用"你/我"，多用"应该/需要/避免"；不写套话。
- **不堆定义**：篇幅给"为什么"和"怎么用"。
- **表格与代码优先**：能表格就表格，能代码就代码；要画图就画 SVG，别为省事塞 mermaid 或 ASCII 框。
- **不注水**：删掉"总而言之""正如我们所见"等空话。
- **中文环境默认简体中文**；代码、术语保留英文原词。

## 代码类笔记（技术主题必读）

技术主题的代码不能只贴一段。遵循**五要素**规范，详见 `references/coding-note.md`：
完整可运行代码 → 输出结果 → 执行流程 → 核心源码位置 → 常见修改方式。

## 用户素材处理

- 素材是代码/文档时：先通读提炼真实行为，不凭印象写。
- 用户要求"不按代码顺序写、不提代码出处"时：写成**纯知识点体系**（按知识逻辑组织，不标注来源文件）。
- **引用可移植性（自包含，笔记必须能"发给别人 100% 看懂"）**：正文引用用户素材（如 `Demo02.java`）时，**不得裸引用外部文件名**——读者或未来的自己看不到那个文件。四件套：
  1. **场景段摘抄关键代码**：把"为什么需要"里描述的那几行核心代码**直接摘抄**进正文（行内代码或 3~6 行小代码块），读者不跳转就明白。如 `**场景**：……每个线程执行的是 \`if (stock > 0) { stock--; }\`——注意 \`stock--\` 是"读-改-写"三步（完整代码见第三节）`；
  2. **完整代码放「核心代码」节**：场景段只摘关键行，全文代码集中在第三节，避免重复；
  3. **代码块不写类名**：**不要出现 `public class Xxx {` 这类类声明行，也不要用任何名字（`Demo0X`/`Test0X`/`SecKillDemo` 都不行）**——任何名字对读者都是歧义，别人不知道这份代码是什么。代码块直接展示类内逻辑（字段/方法体/`main`），需要时加一行注释 `// 完整可运行代码（类名自拟），以下为类内逻辑`；代码内引用类成员时去掉类名前缀（`Demo04.LOCK` → `LOCK`）；
  4. **溯源放 frontmatter `source:` 字段**：`source: "Date0803/Demo02（1000 线程秒杀库存）"`——给自己回看时找回原文件，给别人看不影响理解正文。
  - **全局禁用**：正文/标题/代码块内**一律不出现** `Demo0X`、`Test0X` 及任何示例类名（小节标题用功能描述：`thenApply 链`、`令牌桶限流`，不用 `Demo03`、`Test01`）。
  - 自检标准：**把笔记发给一个没见过你代码的人，他能完整读懂、能复制运行、能讲出原理，才算合格**。
